### 🔍 G-Arch 代码评审 (Code Review)

#### 1. 数据建模：扁平化 + Field Collapse (绝佳的 Pivot)
**👨‍💻 G-Arch 点评：Outstanding (极优)**
你没有盲目听从我在需求里挖的坑（“必须解决跨字段匹配”通常会引导新人使用 Nested）。你意识到**库存更新是电商最高频的操作**，如果用 `nested`，库存一变，整个商品文档都要 Reindex，这在高并发下是灾难。
你选择了**“按 SKU 扁平化存储 + 搜索时用 `product_id` 进行 Field Collapse（折叠去重）”**的架构。
*   **优点**：写入极度轻量，更新单 SKU 库存只需 Update 单个极小的文档。跨字段匹配问题天然不存在（因为每个文档就是一个独立的 SKU）。
*   **Trade-off 确认**：这种设计牺牲了一点点查询组装的复杂度，以及聚合统计时的准确性（如果按商品统计，可能会被 SKU 数量放大，需要配合 `cardinality` 聚合去重）。但在这个场景下，这是**最正确的妥协**。
*   *小提示*：你的 `price` 类型用了 `long`。在 Google / 常见大厂，这通常代表**“金额的最小单位（如分/Cent）”**。如果你的系统是这样约定的，完美，避免了浮点数精度丢失；如果你本意是存浮点数，ES 中推荐使用 `scaled_float`。

#### 2. 容错批量写入 (Resilient Bulk Ingestion)
**👨‍💻 G-Arch 点评：Strong (优秀，但留有隐患)**
你提到了 Exponential Backoff 和 Jitter（防惊群效应），这证明你具备优秀的 SRE 防雪崩意识。你也精确区分了 `429`（重试）和 `400`（不重试）。
*   **毒药机制（Poison Pill）隐患：** 你在代码里图省事，只要 `response.errors()` 为 true 就抛出异常重试整个批次。你在注释里也意识到了。我必须强调，在生产环境这绝对不行。假设一个 Batch 有 1000 个文档，其中 1 个文档因为字段类型冲突（比如把字符串传给了日期字段）报 `400 Bad Request`，另外 999 个成功。由于你整体重试，那 999 个文档会反复无意义地写入，而那个坏文档永远过不去，最终导致线程池堵死。**正确的做法必须是：遍历 `BulkResponse`，挑出状态码为 `429` 的 `item`，重新组装成一个新的 `BulkRequest` 专门重试。**

#### Answer

场景一:
alias是重建索引的标准解决方法, 在实际开发中, 不应该让java业务代码访问真正的索引, 永远访问的都是索引别名, 例如我们完成的项目中products索引在实际开发中应该建立一个别名: `products_alias`, 然后java代码始终访问这个别名, 当需要数据迁移时, 我们新建一个索引 `products_v1`, 迁移完成后在此通过alias使其别名也为 `product_alias` , 然后取消 `products` 的别名, 这个耗时极低. 当然为了防止确实在这么短暂的时间内有请求过来, 系统自然也需要通过消息队列等中间件缓存请求, 但显然这么短暂的请求堆积不会导致系统崩溃
原子性切换： 你提到的“瞬间有请求过来导致崩溃”其实在 ES 层面是不存在的。ES 的 _aliases API 支持在同一个请求里同时执行 add 和 remove。这是一个原子操作（Atomic Operation），对于 Java 客户端来说，流量切换是 0 毫秒的无缝衔接。
- 深坑（Delta 数据同步）： 真正的难点在于：_reindex 1.5TB 数据可能需要几个小时。在这个过程中，线上 products 源索引还在不断有新订单写入。怎么保证这部分“增量（Delta）”不丢？
- 标准做法： 在业务代码里开启“双写”（写旧索引的同时也写新索引），或者像你说的，利用 MQ 将这几个小时的修改事件积压起来，等全量 Reindex 完成后，再消费 MQ 追平增量，最后执行 Alias 原子切换。


场景二:
真实数据量的大小为1.5TB*1.2/0.85=2.118 TB, 部署到生产环境, 由于是商品数据, replica建议设置为2, 因此数据量大小提升为6.354TB, 商品数据的查询多, 因此分片大小建议10-20GB, 假设为15GB, 则分片数应该设置为2.118TB / 20GB =105.9 个分片, 考虑到大量分片会导致集群维护状态以及FST占用内存过大, 建议按照商品热度进行hot-warm架构, warm架构上的数据可以考虑缩容分片和段合并
- 分片大小： 对于搜索密集型（Search-heavy）的电商场景，单个分片 10GB - 20GB 是黄金区间。你的计算完全正确。
- 架构优化： 算出来 105个主分片是对的。但在单索引里放 100 多个分片会让 Cluster State 有点重。在真实的电商大厂，我们会采用Routing 或拆分索引。比如按照商品的一级类目（3C数码、服装、食品）拆分成 products_3c、products_clothing 等，并在上面盖一个全局的 Alias。

场景三:
- 慢日志阈值： 在电商核心链路，1 秒已经是“重大事故”了。用户的搜索耐心只有几百毫秒。我们通常的 SLA 是 P99 < 150ms。因此，Query 阶段的 warn 应该设为 200ms，info 设为 50ms。
业务层熔断（除了超时控制）：
- 查询复杂度拦截： 在 Service 层，限制用户最多只能输入 10 个关键词，或者勾选最多 5 个筛选项。拒绝生成过于庞大的 Boolean Query。
- 深度分页物理阻断： ES 有一个 index.max_result_window 参数（默认 10000）。在业务网关层也要强控，不允许任何请求 from + size > 10000，直接返回 HTTP 400 告知业务方使用 Search After/Scroll。
